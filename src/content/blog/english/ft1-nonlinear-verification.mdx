Every FT-1 controller posted so far — single-loop, cascade, gamma/speed-hold — was designed against one thing: a 12-state model produced by linearizing a Simulink airframe about straight-and-level trim. Linearizing is a small-signal approximation by construction; up to this point, the nonlinear aircraft model had never actually been checked against it. This post compares the linear model against the nonlinear one to verify both are accurate — if the model itself isn't right, every controller built on it is a castle in the air — plus it answers a question none of the controller posts needed to ask: with nobody flying it at all, what does FT-1 do, and how long before it goes out of control?

## Comparing the linearized and nonlinear models

This reuses the same Simulink "airframe" harness — Aerospace Blockset 6DOF (Euler Angle) plus an AVL-derivative aerodynamic buildup — that produces FT-1's linear model in the first place, but run open-loop instead of trimmed-and-linearized: release a small disturbance from trim, no controller, and watch the full nonlinear equations integrate forward. The companion linear run takes the same disturbance through the actual linearized state matrices. Same underlying block diagram either way, which makes this a self-consistency check: does linearizing this harness match running it.

## Longitudinal: a similar response, but offset in time

![FT-1 longitudinal open-loop response: linear vs genuine Simulink nonlinear model, +1 deg/s pitch-rate disturbance, showing a growing phugoid phase drift](/images/ft1-nonlinear-verify/ft1-openloop-long.png)

The pitch axis doesn't match this cleanly, and it's worth showing the plot that says so rather than only the one that doesn't. +1 deg/s of pitch rate excites FT-1's phugoid — the slow trade of speed for altitude every fixed-wing aircraft has — and for the first cycle or two, linear and nonlinear track together. By the third oscillation, they've drifted about a quarter-period out of phase: the nonlinear model's phugoid runs measurably slower than the linear model's own eigenvalues (`-0.011 ± 0.627 rad/s`, a 10.0-second period) predict. This is the textbook signature of a genuinely nonlinear effect a linearization can't carry by construction — finite-amplitude oscillations don't have to share a small-signal model's frequency, even when the underlying equations are correct — not a bug in either model. Flagged here rather than smoothed over: a materially large-amplitude longitudinal maneuver should not be assumed to inherit the linear model's timing without checking.

## What FT-1 does with nobody flying it

The genuine Simulink nonlinear model is also just an aircraft anyone can release from trim and watch. Extending the same lateral disturbance run from 20 seconds to 120, with every actuator pinned at its trim value the entire time:

For almost a minute, the flight attitude stays relatively stable. Then the mildly unstable spiral mode starts to diverge: **φ reaches 5° at t≈56s, 10° at t≈69s, 30° at t≈92s, 45° at t≈107s, 60° at t≈126s** — a slow, accelerating roll-off with no sign of arresting itself, descending as it goes (about 19 meters lost over the 120-second run). None of it is fast. All of it is one-directional. This is the same mode every FT-1 attitude-hold controller posted so far has been quietly correcting.

## What this sets up

Every number in this post — the phugoid drift, the spiral time-to-divergence, the nonlinear model's agreement with the linear one — depends on FT-1's control-derivative units being modeled correctly, which they weren't until a bug found afterward: AVL's `CONTROL` derivatives are per **degree**, not per radian like the rest of AVL's output, and the shared trim/linearize script had been treating them as per-radian. Fixed at the source and re-verified here; see the [PID series' own update notes](/blog/ft1-thrust-gamma-speed-hold/) for the fuller account of what that bug did to every controller's reported gains and deflection angles. This post's own numbers are all post-fix.
